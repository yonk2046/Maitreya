## 1. 診斷：為什麼總是「隔天」

現有的兩道驗證面：

| 驗證 | 涵蓋 | 固定在 |
|---|---|---|
| `make test` | 邏輯正確性 | **執行的那一刻** × 凍結語料 |
| `verify_all_replay` | 歷史決定性 | **執行的那一刻** × 已歸檔的過去 |

兩者都是**單一時刻**的快照。但 pipeline 實際活在一個四軸狀態空間裡：

- **T 時刻**——盤前 08:35 / 盤中 09:00–14:00 / 盤後 19:00 / GHA 20:00 / cron 漂移後的任意時刻
- **D 日型**——交易日 / 週末 / 國定假 / 颱風假 / 連假後第一天
- **M 執行者**——Mac launchd（開機才有）/ GHA / cron-job.org / 兩者同時（race）
- **U 上游**——T86 晚發布 / CDN 對機房 IP 封鎖同日資料 / 來源回空 → 退回 cache

`make test` 跑在星期二上午十一點，它**結構上不可能**變動 T、D、M、U 任何一軸。
於是這四軸構成的整個象限是測不到的——而那正是事故住的地方。

**所以「隔天壞掉」不是改動本身有錯，是驗證面有一個固定形狀的洞。**
我在洞外面驗到綠燈，pipeline 在洞裡面跑。

## 4. 索引設計：小北百貨的走道編號

主索引不放內容，只放走道號。每一列長這樣：

```
| ID | 失效模式 | 軸 | 症狀（你會先看到什麼） | 根因 | 守門員（可執行） | 案例 |
```

設計上只有一條規矩，但它是全部的重點：

> **「守門員」欄必須指名一個真的會跑、會紅的東西**——一顆測試、一個 hook、一個 CI step。
> 填不出來的列，就誠實留白。**留白的列＝已知破口，那一欄就是工作佇列。**

這一條讓索引不會退化成又一份沒人讀的文件：它的每一列要嘛是活的防線，要嘛是待辦。
不存在「寫了但沒用」的中間態。

## 5. 對應你聽到的「神龍引擎」四步

| 神龍四步 | 你這裡的現況 | 缺口 |
|---|---|---|
| ① 錯誤捕捉 | `lessons.md`(9 條,2026-09-15) | 7 月捕捉率偏低;9 月事故已同日寫回 3 條 |
| ② 尋找盲點 | **本檔**(2026-07-28 落地) | 已補上;9 月新增 F-8~F-15 即為此格的產出 |
| ③ 建立最高原則 | 憲法 C1–C12＋修正案流程 | 有，但教訓流不進去 |
| ④ 全域同步 | `.claude/rules/*.md` 自動載入＋hooks | 有，機制健全 |

**你缺的不是①③④，是②。** ①在記事、③④在執行，中間沒有人把散落的事故**歸軸**，
所以「每次都是同一類問題」這件事沒有任何地方會浮現出來。
第 2 節那張表就是②的產物——一做出來，「五件事都在時間軸上」立刻自己跳出來。

### 一個我不同意講座的地方

講座說 AI 發現規律後「**自動去修改自己的底層架構**」，全自動 90%。
**在這個 repo 我建議不要。** 你的憲法管的是判斷參數——一次錯誤的自動改寫會無聲汙染回測，
而且因為 replay 是決定性的，錯誤會被固化進歷史。你既有的「判斷參數＝修正案級＋需核准」
紀律是對的，不該為了自動化拆掉。

**建議的自動化界線：①→② 全自動，②→③ 停下來給你核准。**
機器負責「發現又是同一類」，人負責「所以要立什麼法」。

## 7. 維護規矩

- 每次事故**修完的同一個 commit**裡增列一行（趁上下文還在，不另開任務）。
- 新列若填不出守門員，**照樣寫入並留白**——留白才會被看見。
- 同一「軸」累積到 3 列，就是訊號：該往憲法提修正案，不是再補第 4 顆測試。
- 本檔只增不改；已修好的列保留（它是守門員存在的理由，刪掉下一個人就會拆掉測試）。
